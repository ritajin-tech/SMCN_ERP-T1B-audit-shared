## 0. 一句话

生产表里有 1612 行、共 7238.5 小时的工时，**从来没进过主库，而且以后也永远不会进**——因为同步程序遇到它们时直接跳过，**不抄、也不报错**。

## 1. 机制（为什么会这样）

`syncProdToMaster` 每天把生产表的新行抄进主库底稿。为了不重复抄，它记了一个**水位线**：底稿里最大的录入时间。程序只抄"录入时间晚于水位线"的行，比这早的就当"早就抄过了"，`continue` 跳过。

问题：有 1612 行**录入时间早于水位线**（当前水位线 = 2026-10-25 18:03:17 北京），但**底稿里根本没有它们**（UUID 不在、内容键也不在）。于是：

- 程序认为"抄过了" → 跳过
- 底稿里其实没有 → 从未抄过
- **两边都不报错** → 长期静默悬空

其中 **1154 行 UUID 为空**（UUID 启用前的老行），只能靠内容键匹配；而内容键是 `姓名+小写项目号+工时+北京日期+备注`，备注写法稍有差异就匹配不上——这是它们匹配失败的直接原因。

## 2. 影响面

- **主库少算 7238.5 小时**。任何只看主库的报表、汇总、成本核算都会偏低。
- **无法自愈**：水位线只会往前走，这些行永远追不上。
- **无告警**：这是最危险的一点——程序不报错，所以四个月来没人发现。

## 3. 三个选项与推荐

| 选项 | 做法 | 代价 |
|---|---|---|
| A 直接补录 | 把 1612 行全部抄进底稿 | 若其中含重复副本，会把冗余一起带进主库，制造新的脏数据 |
| B 判为冗余 | 全部软标，不再管 | 若其中含真实工时，等于**永久丢弃 7238.5h 真实工作量** |
| **C 先修程序再对账（推荐）** | ① 改 `syncProdToMaster`：遇到"早于水位线但底稿没有"的行**不再静默跳过**，改为显式计数并单独报出；② 再拿这 1612 行做一次对账，按六级分类（UUID 唯一命中 / 内容键命中 / 真挂起）分别处置 | 需要改一次 GAS，但**一次解决、以后不再发生** |

**推荐 C 的理由**：A 和 B 都是在**信息不全**的情况下做不可逆决定。而这 1612 行里，有 458 行带 UUID、1154 行不带——两类性质不同，应该分开处置。更重要的是：**不修程序，这次清完还会再产生下一批**（水位线每天在涨，任何一次匹配失败都会沉淀成新的挂起行）。

## 4. 程序修复方案（长期，非 workaround）

`masterAttendanceLive.js` 的 `syncProdToMaster`（82-128）当前逻辑：

```
for 每一生产行:
    if (UUID 在底稿 || 内容键在底稿) continue;      // 已抄过
    if (录入时间 <= 水位线) continue;                 // ← 问题：静默跳过
    appendRow(...)
```

改为：

```
for 每一生产行:
    if (UUID 在底稿 || 内容键在底稿) continue;
    if (录入时间 <= 水位线) {
        orphanCount++;                                // 不再静默
        orphanRows.push(该行摘要);
        continue;
    }
    appendRow(...)

// 函数末尾：orphanCount > 0 时写一条可见日志/告警（页签或邮件），
// 让人知道"有 N 行早于水位线但底稿没有"，而不是无声无息
```

要点：
1. **只增加计数与告警，不改变写入行为**——不新增任何自动写入，风险最小。
2. 告警落在可见位置（例如主库一个 `_SYNC_ORPHANS` 页签或每日邮件），不再是静默。
3. 这个改动**不换链接**：仅 `clasp push` 到 @HEAD。

## 5. 对账方案（修完程序后做）

拿到 orphan 清单后，按既有六级口径分：

1. **UUID 在主库有唯一命中** → 其实已被 UUID 匹配覆盖，不会进 orphan（正常）。
2. **UUID 不在、内容键在主库命中** → 已覆盖，不会进 orphan。
3. **真 orphan** → 才是这 1612 行。再分两层：
   - 带 UUID 的 458 行：UUID 是生产的唯一码，说明是 `appendRows` 写入的，可回溯录入时刻与操作来源；
   - 不带 UUID 的 1154 行：需按内容键宽松匹配（去掉备注字段）再试一次，匹配上的补录，匹配不上的单独列表人工看。

**建议顺序**：先修程序 → 跑一次拿到 orphan 清单 → 按上面分层处理。不要在没有清单的情况下直接补录或删除。
