## 0. 现状（P0 已上线）

**根因（两 bug 同一坑）**：`google.script.run` 无客户端超时。一旦某服务端调用卡住（最常见是 `updateTimesheet` 抢 `LockService.getScriptLock()` 被占用），既不成功也不失败 → 全屏 `#loader`(z-index 999) 永久遮罩 → **既挡住日期控件（日历点不了）又无限转圈**。

**P0 已做（Rita 批「好」）**：
- `Index.html` 全局重写 `google.script.run.withSuccessHandler/withFailureHandler`，每次调用挂 **35s 超时兜底（RT=35000）**：超时且 loader 仍显示则强制 `toggle(false)` + 提示刷新重试；任一回调即 `disarm()`。只清遮罩、不改任何写入/冻结/PeriodLock 逻辑。
- 版本 `APP_VERSION` / `TS_APP_VERSION` 同升 **4.3.72 → 4.3.73**（强制客户端刷新生效）。
- 经 `clasp` 从真实目录 `/tmp/dss_clasp` 操作（避开 Workspace 符号链接 reparse 致 clasp 拒跑）；先 `clasp pull` 完整 HEAD 再改；改后 `clasp push` 再 **原地 deploy 两个 @193 部署**（`AKfycbzUyhyK`→@194、`AKfycbwYXV3`→@195）。**URL 一个未变、部署数仍 3**（推后 `clasp deployments` 复核实证）。
- **写路径未动**：`submitBatch`（Code.js:412）、`updateTimesheet`（Code.js:485）均经 `_plGuardedInsert`（Code.js:464，PeriodLockGuard）。

## 1. 人本优化：一键补填（P2）— v3 修订

### 1.1 痛点
- 漏打卡（`heat-miss` 日）目前只能进「明细补录」页，**手动选日期 + 项目 + 阶段 + 工时**，步骤多、需记忆、易错。
- **用户诉求（2026-11-02 13:40 北京）**：点一下就能补，**不用自己输入日期**。

### 1.2 设计 A — 日历格点击补填（单日，最直觉，零日期手输）
- **改动点**：`renderHeatmap()`（`Index.html:1215`）生成的 `<div class="heat-cell ...">`，当 `cls==='heat-miss'` 时加 `onclick="openFillFromCell('${ds}')"` 与 `style="cursor:pointer"`。
- **新增 `openFillFromCell(ds)`**：弹出紧凑补填面板。`date` 字段**直接以 `ds` 文本显示（只读，非 `input type=date` 手动选）**，project/stage/hours 由 `inferPattern(ds)` **作为「建议值」预填**（来源在面板内标注），用户确认/微调后才提交 → 调 `submitBatch(currentToken, [{date:ds, project, stage, hours, notes}])`（Code.js:412，经 PeriodLockGuard）。
- ✅ **满足「不用自己输入日期」**：日期源于日历格坐标，页面上不出现任何日期输入框。

### 1.3 设计 B — 一键补全整月漏填（最高效，v3 强化预览）
- **入口**：heatmap tab 顶部加按钮「⚡ 一键补全 N 天漏填」（N = `renderHeatmap` 已算的 `miss` 计数，`Index.html:1241`）。
- **`inferPattern()`**：复用只读 `getDetailLogsByMonth`（Code.js:265，返回 `{date, stage, project, hours, notes}`）取目标月/邻近月已填行，按星期几（dow）聚类，取 **mode(project) + mode(stage) + 中位数(hours)** 作该星期几模板；输出**仅作「建议值」**，并附「推断来源」（如「基于同星期三 8 条历史记录的众数」）。
- **预览确认（v3 关键修订）**：对所有 `heat-miss` 日生成 fill 行 → 弹「**预览确认**」表，每行含 5 列：**日期 / 项目 / 阶段 / 工时 / 推断来源**，每行带 **复选框（默认勾选，取消=排除该行）**；项目/阶段/工时均可**逐项手改**；**由填报人点「确认补全」才提交**。
- **留空与禁静默批量（v3 关键修订）**：`inferPattern` 对「历史样本 < 阈值（建议 3 条）」或「众数并列 / 方差过大（冲突）」的日，输出**空值**并在来源列标注「无可靠历史 / 冲突」，该行**默认不勾选且置灰**；**禁止任何无确认的全量自动填充**。
- **安全复用**：`submitBatch` 已有批内去重（Code.js:418-445）+ 10 分钟幂等窗 → 重复点/误点不双写。

### 1.4 写入闸门（与 T1-B 对齐，关键）
- 写路径 = `submitBatch` → `_plGuardedInsert`（Code.js:464，PeriodLockGuard）。**当前 `TS_WRITE_FREEZE` 锁定 + Tom 未发 clearance → 写被拒（预期行为）。**
- **冻结的唯一有效执行点是服务端 `_plGuardedInsert`（Code.js:464 / PeriodLockGuard.js）**；前端按钮/面板在冻结期置灰**仅是 UX 提示，不构成冻结保障**（吸收 Tom 原则6）。
- **分两阶段交付**：
  - **阶段①（现在就能做，纯前端 + 只读 API）**：日历格可点、补填面板、`inferPattern`、预览确认 UI 全做；按钮/面板在冻结期置灰显示「⏳ 等待根因修复放行（T1-B 冻结中），补全暂不会写入」，**绝不弹"成功"假象**，且安全结论以服务端拒绝为准。
  - **阶段②（Tom 放行根因修复 + 解除冻结后）**：无需改代码，写自动生效（`submitBatch` 走通）。
- **红线**：只推 HEAD、同 URL、部署数 = 3 不变。

### 1.5 v3 吸收 Tom 14:19 的 6 条审阅原则（关键修订）
