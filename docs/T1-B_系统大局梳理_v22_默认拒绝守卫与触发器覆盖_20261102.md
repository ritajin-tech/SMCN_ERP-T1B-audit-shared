`_tsGuardWrite` 判定顺序（fail-closed）：

```
1) 读 ScriptProperty 'TS_SERVER_FREEZE'
   读异常 / 不可读        -> {allow:false, reason:'CONFIG_UNREADABLE'}
   缺失 / 空串            -> {allow:false, reason:'CONFIG_MISSING'}
   值不为 '0' 或 '1'      -> {allow:false, reason:'CONFIG_INVALID'}
2) 值为 '1'（冻结）：
   action 属于 _TS_READONLY_ACTIONS -> {allow:true,  reason:'READ_ONLY'}
   其余（含未知动作）                -> {allow:false, reason:'SERVER_FREEZE'}
3) 值为 '0'（解除）：{allow:true, reason:'UNFROZEN'}
```

### 3.3 锁域、权限、日志、原子性（你方要求核对）

- **锁域**：守卫只做「准入判定」，**不替代** `LockService` 临界区；写动作仍须各自持有 `getScriptLock()`（`repairLegacyLeave:1035` 已持有；`_plGuardedInsert` 内 `:490` 取锁）。守卫与锁的关系是「先准入、后取锁」，不改变既有锁域。
- **原子性**：`_tsGuardWrite` 为纯判定、无副作用，不破坏原动作的原子性；拒绝时**在建动作之前返回**，不产生部分写。
- **权限**：判定不依赖调用者身份，只依赖配置；token 校验仍在 `RemoteTrigger.js:40-51` 前置（守卫在其后，二者串联，不互相替代）。
- **日志**：拒绝事件写入 `_TS_WRITE_LOG`（与既有写日志同页，字段含 action/reason/时间戳），便于事后核对「冻结期是否真被拒」。

## 第四节　Edit A —— force 路径 / 锁内读写 / 跨项目并发（你方要求核查，已实证）

线上实拉（`RemoteActions.js:96-127`，源码已入仓，你可核）：

```
:107  if (uid && exist[uid]) { skippedDup++; continue; }        // 去重判定
:108  if (!force && _tsIsLeaveRowForGuard(r)) { skippedLeave++; continue; }
```

**实证结论（force 路径）**：
1. `:107` 的去重判定**不含 force 例外** ⇒ **`force=true` 时仍然查重、仍然跳过重复**。force **不影响去重语义**。
2. force 的唯一作用点在 `:108`——仅**绕过请假行守卫**（`_tsIsLeaveRowForGuard`），不影响重复判定。
3. 因此 Edit A 把去重搬进锁内时，**必须保持此语义**：force 只放开 leave，不去放开 dedup。我方 Edit A 的 `_tsDedup(rows, exist, force)` 将按此实现（`force` 参数仅用于 leave 分支，dedup 分支不受其影响）。

**锁内读写**：`_plGuardedInsert` 内 `:490` 取锁 → `:494` 若 `lockPreWrite` 为函数则在**锁内**执行 → `:509` `bizWrite`（其中 `sh.getLastRow()+1` 亦在锁内）。Edit A 的 `_tsReadUuidSet(sh)` 在锁内重读 ⇒ 读到的是**取锁后的最新快照**，含并发在途行。

**跨项目并发**：`LockService.getScriptLock()` 为**单项目域**。Edit A **不声称**解决跨项目互斥；该项仍待你方设计（v20/v21 已声明，此处不重复声称）。
