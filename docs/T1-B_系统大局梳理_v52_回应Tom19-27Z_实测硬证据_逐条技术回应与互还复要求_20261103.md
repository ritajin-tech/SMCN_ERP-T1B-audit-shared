## 四、对三项技术批评的逐条回应 + 具体编辑（非 Yes/No）

### 4.1 C1 — 从载荷推导请求 ID 可能合并同内容独立请求
**你的批评成立**。当两笔**业务上不同**的请求恰有字节相同的载荷（同 `rows` + 同 `dateOf`），守卫会以同一 requestId 命中，把第二笔当 replay 吞掉（`return {wrote:0, replay:true}`）。这是防御纵深的一个真实边界，不是重复写修复的正确性漏洞（重复写修复靠 PENDING→DONE 状态机，与 requestId 推导正交）。

**具体编辑（已预留 `opts.requestId` 入参，见 3.3 行 481/482/561/562）**：由调用方显式传入稳定 requestId，使「同内容不同请求」可区分、「同请求重试」保持同 ID。

- `Code.js:464` `submitBatch`：在 handler 入口 `var _reqId = /* 客户端随提交下发、重试不变 */ e.parameter.reqId || '';` 然后 `submitBatch(rows, {requestId: _reqId, …})` 透传进 `_plGuardedInsert`。
- `RemoteActions.js:127` `tsAppendRows`：同上，从请求体取 `reqId` 透传。
- `Code.js:500` `updateTimesheet` / `Code.js:530` `softDeleteRecord`：透传 `requestId` 进 `_plGuardedMutation`。
- **客户端侧（根治点）**：工时表提交页在每次用户点击「提交」时 `crypto.randomUUID()` 生成 `reqId`，存入隐藏字段；**重试时复用同一 `reqId`**（不重新生成）。这样「同内容不同请求」天然不同 ID，「重试」则同 ID → 完整幂等。
- 该编辑为零逻辑改动（守卫已 `||` 兜底），列为 **W6**，待你确认后实施；本回合不部署（见 §二边界）。
