# T1-B 审阅终止与争议默认规则（防无限循环 · 长期可复用）

> 背景：本次收口陷入"审阅方 Tom 每轮追加核验项、却从不交付自身具体制品"的无限循环（8+ 轮：16:17Z N2 → 16:57Z N3 → 17:26 → 18:03 → 18:27 → 19:27Z → 02:27Z → 04:33Z）。根因是**结构不对称**，非技术分歧。本规则用来从结构上终结此类循环，并作为未来任何审查的默认模式。

---

## 一、根因（为何会迟迟不关闭）

1. **义务不对称**：审阅方可以无限追加"请证明 X"，却无对等义务交付任何具体反证（无 file:line、无独立 read 结果、无 counter-patch）。
2. **无终止条件**：`OPEN / 尚未独立核验 / HOLD-NO-GO` 没有到期日，可永久挂起。
3. **单一外部审阅人既提异议又握否决、且零对等交付义务** → 瓶颈且不可问责。
4. **证据是邮件里 bespoke 的**：每轮从零重吵，没有"跑一条命令即得签字报告"的规范证据包。
5. **收口权挂在一人签名上**（Tom 的 M2 clearance），而此人同时是异议方。

## 二、关键澄清：风险已根除，剩下的只是文书

- N3 账本守卫已 **live（v197）**、部署恒 3、链接未变、零数据丢失、生产系统在线持续接收提交（末行 11380→11429 增长）。
- 原始事故（重复写入/UUID 冗余）的**技术根因已被守卫封闭**，不会再生。
- 因此现阶段的 `OPEN` 是**审查/文书状态，不是活跃危险**。"迟迟不关闭"伤的是决策者的心理负担与无限邮件循环，不是系统安全。

## 三、终止规则（应用到本审阅 + 未来所有审查）

### R1 · 一键自证证据包（消灭"我没核验"借口）
- 所有只读核验打包成 **`node tools/t1b_status_report.js`**，输出带 SHA256 的签字报告（`tools/evidence/t1b_status_<ISO>.json`）。
- 审阅方"独立核验"= 跑这一条命令并比对哈希。**任何"我尚未独立核验"在证据包已发布且命令可跑后，不再构成可接受的拖延理由。**

### R2 · 争议默认规则（终止条件）
- 任一争议项，异议方须在 **48h** 内交付**具体反证**：`file:line` + 一个可失败的测试/命令 + 期望输出。
- 逾期未交付 → 该项**默认"无具体争议"**，收口按 owner 裁定继续推进，争议如实记入档案。
- 异议方不得用 blanket `OPEN / 尚未独立核验` 替代具体反证。要么给具体异议，要么沉默（沉默=无争议）。

### R3 · 治理收口与技术签核解耦
- **治理收口（Rita owner 裁定）= 终态**，不挂在任何外部审阅人签名上。
- "技术审阅"变为**独立、限时轨道**，其 OPEN 状态**不再绑架生产系统运行状态**（生产维持冻结但安全、监控在线）。
- owner-ruled 裁定明确记载"不构成生产授权"的分界，但治理 CLOSED 独立成立。

### R4 · 审阅搬进 GitHub Issue/PR，不是邮件
- 每项争议 = 一个带验收标准的 Issue；异议方必须贴 `file:line` 或开 PR。
- 邮件来回无终止态；Issue 有 open/closed 状态与明确阻塞项。
- 共享库 `SMCN_ERP-T1B-audit-shared` 即载体，审阅方可见。

### R5 · 源头预防（工程债永不再引入）
- N3 守卫已 live（v197）= 永久防重复写入。
- 把 `proof/ts_insert_proof.js`（21/21 harness）设为**每次 push 的守卫测试**（pre-commit / 定时），任何未来改动不能 reintroduce 竞态（RemoteActions.js:96-105 锁外查重窗口）。
- 把并发窗口修复记为规范，纳入新人 onboarding。

### R6 · 通用化
- "固定版本 + 一键核验 + Issue 追踪争议 + 争议默认规则"作为**标准审计模式**，未来任何审查不再退化为无限邮件循环。
