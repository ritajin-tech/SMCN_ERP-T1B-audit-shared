### B-edit-1 · `RemoteActions.js` 第 96–105 行（去重读移入锁内）

**现状（快照行号）**：
```js
96  // 已存在的 UUID（含软删行，避免把已删数据复活）
97  var last = sh.getLastRow();
98  var exist = {};
99  if (last > 1) {
100   var uuids = sh.getRange(2, 9, last - 1, 1).getValues();
101   for (var i = 0; i < uuids.length; i++) {
102     var u = String(uuids[i][0] || '').trim();
103     if (u) exist[u] = true;
104   }
105 }
```
**问题**：该块在 `tsAppendRows` 调用 `_plGuardedInsert`（第 127 行）**之前**执行；而锁在 `PeriodLockGuard.js:490` `_plAcquire` 才获取。于是 **第 105 行（exist 读毕）到第 509 行 `bizWrite` 之间**存在一个并发窗口——此间另一写者（含跨项目写者）若插入同 UUID 行，本 `exist` 地图不会捕获 → 重复行。这正是你要求的「去重读取须在共享协调机制内完成」所针对的缺口。

**改法（草案）**：
1. 删除第 96–105 行（前置去重读）。
2. 在第 127–138 行的 `_plGuardedInsert({…})` 调用中增加 `lockPreWrite(rows, policy)` 钩子，使其在锁内（PeriodLockGuard.js 第 490 行之后、第 494–498 行空实现处）重读 `sh.getRange(2, 9, last - 1, 1)` 并过滤重复 UUID，返回 `{ rows: filtered, duplicates: n }`。
3. 同批去重（原第 113 行 `if (uid) exist[uid] = true;`）改由锁内读结果 seeded。
4. `bizWrite`（原 130–137）保持锁内写，消费过滤后 `rows`。

**验收映射（你的 5 条）**：并发重复请求 → 第二次同 UUID 在锁内被拦；部分失败与重试 → 重试须重跑整段 `_plGuardedInsert`（重新获取锁 + 锁内重读去重），不得盲写。

### B-edit-2 · `PeriodLockGuard.js` 第 490–509 行（闸门：确认锁内线性化）

**现状（快照行号）**：
```js
490  lock = _plAcquire(opts.timeoutMs);
491  var policy = _plPolicy();
492  var rows = opts.rows;
493  var duplicates = 0;
494  if (typeof opts.lockPreWrite === 'function') {
495    var pr = opts.lockPreWrite(rows, policy);
496    rows = (pr && pr.rows) || [];
497    duplicates = (pr && pr.duplicates) || 0;
498  }
499  if (!rows || rows.length === 0) {
500    return { wrote: 0, duplicates: duplicates, skippedAll: true };
501  }
502  var post = _plGuardCheckBatch(rows, opts.dateOf, policy);
503  if (!post.ok) { var e1 = new Error(post.reason + ' @row#' + post.index); e1.plCode = post.reason; throw e1; }
504  enteredWrite = true;
505  var result = opts.bizWrite(rows, policy);   // 509 实际写入，锁内
```

**现状已满足项**：第 490 行获取锁后，第 491 行 `policy = _plPolicy()`（冻结态）在锁内读取 → 已满足你「冻结切换同域线性化」；第 502 行 post-check、第 509 行 `bizWrite` 均锁内。

**改法（草案）**：
1. 将 B-edit-1 的去重读并入 `lockPreWrite`（第 494–498 行空实现），使其**在锁内执行**——使「去重读取」与「写入提交」均落在同一锁临界区内。
2. 确认 `_plAcquire` 失败路径（超时/获取失败）抛 `PL_LOCK_ACQUIRE_FAILED` 并使调用方返回 `{ ok: false }`——覆盖「锁获取失败」验收。
3. 确认 retry 走整段 guard（重新 acquire + 锁内重读去重 + post-check），而非只重跑 `bizWrite`——覆盖「部分失败与重试」验收。
4. 跨项目写者：submitBatch（Code.gs:464）与 tsAppendRows（RemoteActions.js:127）均经 `_plGuardedInsert`（本文件第 479 行定义）→ 同一锁机制，覆盖「跨项目写者是否用同一机制」验收（此点仍需你方独立确认两条入口确都走此 guard）。

**验收映射（你的 5 条）**：冻结切换与写入交错 → 第 491 + 509 行均锁内，不交错；跨项目写者 → 同一 `_plGuardedInsert` 锁。
