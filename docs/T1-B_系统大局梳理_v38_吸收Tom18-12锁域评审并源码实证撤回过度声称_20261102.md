## 1. 针对你核实清单的源码核查结果（基于固定快照，逐条给行号）

### F1 · 你的「切换本身须用同一锁」—— 正确，且是真实缺口
- 锁本体 `_plAcquire`（`PeriodLockGuard.js:259-269`）第 260 行：`var lock = LockService.getScriptLock();` → **项目级锁**。
- **冻结切换 setter `_plSetPolicy`（`PeriodLockGuard.js:170-183`）直接写 `PropertiesService.getScriptProperties()`（171-182），全程未调 `_plAcquire`** → 切换发生在锁外，不与任何写入临界区串行化。这正是你说的「锁内读冻结态不单独证明切换线性化」的精确根因。
- 其唯一调用点 `RemoteActions.js:1071` `setupPeriodLock` → `_plSetPolicy(true, true, 'rita-deploy')`（部署初始化、零业务写），同样无锁。

### F2 · 你的「仅两入口同名函数不足证跨项目互斥」—— 正确；我 v37 对应声称是过度声称，在此撤回并纠正
- `getScriptLock()` 是**项目级锁**，仅序列化同一 GAS 项目内的调用。本快照 18 文件同属 ts-manager 一个项目，故**以下三条写入口在同一项目内被同一把锁互斥**（均经 `_plAcquire`）：
  - `tsAppendRows` → `_plGuardedInsert`（`RemoteActions.js:127`）→ `_plAcquire`（`PeriodLockGuard.js:490`）；
  - 软删/改 → `_plGuardedMutation`（`Code.js:500, 530`）→ `_plAcquire`（`PeriodLockGuard.js:417`）；
  - 字段级改 → `tsPatchCells` → `_plAcquire`（`RemoteActions.js:176`）。
- **但**：静态源码只能证「本快照内同项目互斥」，**不能证「无其他 GAS 项目也在写 TS_ID 生产表」**。这正是你要的负例验收点——需枚举所有对 `TS_ID` 有写权限的部署/项目，确认它们都经上述守卫且同属一把 `getScriptLock()`。我无法从静态源码给出此负例证明，列为 **OPEN 待你/运维核**。我 v37 写「submitBatch 与 tsAppendRows 均经 `_plGuardedInsert` → 同一锁机制，覆盖跨项目写者」是未验证的过度声称，已纠正。

### F3 · 写入口与触发器（你清单第二项）
见 F2 三条。另：`onOpen.js:920-923` 注释提及原 `getScriptLock()` 与 PeriodLockGuard 共用项目级锁（已改 `getUserLock` 处不涉生产表写）；`leave_sync.js:110` / `Code.js:56,95,572` 的 `getScriptLock()` 属其他表/流程，不属生产表去重写路径，不在本次 B 范围。

### F4 · 锁失效与异常失败关闭（第三项）
`_plAcquire` 失败 → `lock.tryLock` 返回 false → 抛 `PL_REJECT_LOCK_BUSY`（`PeriodLockGuard.js:263-267`），调用方走 catch 返回非 ok、不进入 `bizWrite`。即「锁获取失败」验收点已有基础，但仍需负例证明各调用方均正确非阻塞返回（未静默吞错）。此点建议你给负例。

### F5 · 部分写入重试（第四项）

### F6 · 空 UUID 行为（第五项）
