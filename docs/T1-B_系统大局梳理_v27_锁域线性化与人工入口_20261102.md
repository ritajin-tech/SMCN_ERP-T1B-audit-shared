### 4.2 Edit C v4 具体编辑（四项，未部署）

**C-v4-1 冻结翻转纳入同一锁域（线性化时点）**

- 文件：`RemoteActions.js`（新增动作）+ `RemoteTrigger.js`（若需）
- 位置：新增 `tsSetFreeze`；现有 `RemoteTrigger.js:51` token 门控之后
- 问题：当前 `TS_SERVER_FREEZE` 由人工改 ScriptProperties，**不经任何锁**，故与在途写无互斥关系，这是竞态根因。
- 改法：
```js
function tsSetFreeze(p) {
  var v = String(p.value || '');
  if (v !== '0' && v !== '1') return { ok:false, code:'BAD_VALUE' };
  var lock = LockService.getScriptLock();
  var got = false;
  try { got = lock.tryLock(30000); } catch (e) { got = false; }
  if (!got) return { ok:false, code:'LOCK_BUSY_FREEZE_NOT_APPLIED' };  // 不重试、不盲写
  try {
    PropertiesService.getScriptProperties().setProperty('TS_SERVER_FREEZE', v);
    SpreadsheetApp.flush();                       // 若冻结位落在表内
    return { ok:true, value:v, appliedAt:new Date().toISOString(), lockDomain:'getScriptLock' };
  } finally { try { lock.releaseLock(); } catch (re) {} }
}
```
- **线性化时点定义**：冻结生效的线性化时点 = `tsSetFreeze` **取得锁的时刻**。此后任何写者必须先 waitLock，取得锁后重读冻结位 → 必然读到新值。此前已持锁的写者 → 完成落盘后才释放 → 翻转者 `tryLock` 拿不到锁而返回 `LOCK_BUSY`（不盲写、不重试）。
- 验收 V1：写者持锁 5s（注入延迟）期间调 `tsSetFreeze=1` → 返回 `LOCK_BUSY_FREEZE_NOT_APPLIED`，且 `TS_SERVER_FREEZE` **未被修改**；写者释放后立即重试 → `ok:true`。
- 验收 V2：翻转成功后再提交写 → 拒绝且零落盘。

**C-v4-2 在途请求排空**

- 位置：`PeriodLockGuard.js:509`（`bizWrite` 调用处）/`RemoteActions.js:1030`
- 问题：排空的定义不清。
- 改法（**不新增机制，靠锁语义**）：写者**整个写入过程**（含 `setValues` 与 `flush`）必须位于持锁区间内。当前 `_plGuardedInsert`（`PeriodLockGuard.js:479–541`）已满足——`:490` 取锁 → `:509` bizWrite → `:541` finally 释放；`repairLegacyLeave`（`RemoteActions.js:1030–1049`）同样持锁写。因此「在途排空」= 翻转者 `tryLock` 成功即代表此刻无任何在途写。**此项无需改代码，但需写入验收判据**：新增断言「bizWrite 与 flush 必须位于 tryLock/releaseLock 之间」，违反即为 Edit C 未闭合。
- 验收 V3：静态检查——`setValues/setValue/flush` 出现在锁外的写路径数 = 0。

**C-v4-3 跨项目锁域（getScriptLock 失效处）**

- 问题：`getScriptLock()` 为单项目域，拆分出独立 GAS 项目后失效。
- 改法（外部租约锁，具体设计）：
  - 载体：专用协调表（建议独立 ssId，不复用生产表以免锁写污染审计日志）单行 `A1:D1`，字段：
    `A=lockName, B=holderId(scriptId|execId), C=leaseExpiryMs(epoch), D=revision(int)`
  - 取锁算法（CAS）：
    1. 读 (B,C,D) → 若 `C > now` 且 `B ≠ self` → 退避重试 N 次后失败（**不盲等、不强制夺锁**）
    2. 否则写 `(self, now + TTL, D+1)`
    3. 重读校验 `D === D+1 且 B === self` → 成功；否则放弃（并发覆盖检测）
  - 释放：`B = '' , C = 0`（仅当 `B === self`）
- **边界与不做过度声称**：
  - 这是**最终一致**的分布式锁，非强线性化。已知失效模式：①时钟漂移 ②租约过期后在途写仍会落盘 ③协调表本身写入失败。
  - 因此我方**不声称消除跨项目窗口**，只声称：把窗口从「不可见」变为「可检测、可选拒绝、可审计」。
  - 是否采用、TTL 取值、协调表归属，请你方裁定。若你方有更强的方案（如把所有写入收敛到单项目从而根本不需要跨项目锁），请给具体设计，我方采纳。

**C-v4-4 验证失败与部分写入**

- 位置：`RemoteActions.js:1040–1049`（repairLegacyLeave 写入循环）
- 问题：多行循环中逐行/逐块 `setValues`，中途抛错会产生部分写，且当前无「已写块」登记。
- 改法：
  1. 单块写入优先：行号连续时合并为一次 `setValues`（整块原子）。
  2. 必须分块时：维护 `writtenChunks[]`，每块成功后 push；catch 内**立即停止后续块**（不继续），登记不确定（复用 `_plLogUncertain` 语义），并返回 `partial:true, writtenChunks, failedAt`，而非静默返回成功。
  3. 返回值必须包含 `done / skipped / partial / failedAt`，调用方据此决定是否回滚。
- 验收 V4：注入第 3 块抛错 → 前 2 块已写、第 4 块起未写、返回 `partial:true failedAt=3`，且日志登记不确定；V5：整块成功时 `partial=false`。

**C-v4 边界总述**：Edit C v4 解决**单项目内**冻结切换与写提交的互斥与线性化；跨项目仅提供可检测的租约方案，不声称强一致；人工入口见第六节（Edit C 覆盖不到）。

### 4.3 我方 v25 方案作废声明

v25 的「入口判一次 + 锁内二次校验」**予以作废**。理由：检查与写入不在同一临界区，增加检查次数不消除窗口——你方论点成立。v25 的 `_tsFreezeRecheck()` 不再作为 Edit C 的方案，仅保留 `_tsFreezeState()`（三态 fail-closed）作为 v4 的判定函数。
