## 1. 逐点回应（源码实证，基于固定快照）

### L1 · 账本故障窗口 + 授权闸 → 接受，重排为「先预留 PENDING 再写」+ 显式授权闸
- **原 K1 缺陷（你点中，真 bug）**：v42 顺序是「查账无键 → 执行业务写 → 成功后落账」。若业务写成功但落账失败，客户端重试时账本仍无键 → 我方逻辑判「无键 → 执行 + 落账」→ **重复写入**。这是真实故障窗口，接受并修正。
- **修正设计（乐观预留 optimistic reservation）**：
  - 到达带 `requestId`：
    - 账本 **DONE + payloadHash 相同** → 返回已存结果（幂等重放，不重跑）；
    - 账本 **DONE + payloadHash 不同** → 拒绝 `PL_REJECT_REQUEST_ID_MISMATCH`；
    - 账本 **PENDING（任意 payloadHash）** → **在途或结果不明 → 暂停，不执行、不重执行，返回 `UNCERTAIN_PENDING_MANUAL`**（关键修复：PENDING 即「不得假定未执行」）；
    - 账本 **absent** → **先预留 PENDING（业务写之前写账本 PENDING）**；预留失败 → fail-closed，不业务写；然后执行；成功则 PENDING → DONE（带 resultRef）；该转换失败 → 条目仍 PENDING → 重试见 PENDING → 暂停（无重复）。
  - 窗口闭合：预留与业务写之间崩溃 → 留 PENDING（重试暂停，无重复）；业务写成功与 DONE 转换之间崩溃 → 留 PENDING（重试暂停，无重复）；唯 DONE 确认防重执行。
- **失败恢复协议（与 K3/J4 一致）**：PENDING 条目**绝不自动恢复 / 重执行**；独立人工（或显式授权的异步）对账流程用 `businessKey + payloadHash` 查行是否真落库：是 → PENDING→DONE；否 → 人工裁定后补全或标 FAILED。
- **一致性不变量（回应「证明一致」）**：账本状态是「requestId 是否已解决」的权威；DONE = 已确认执行；PENDING = 已执行与否未知，绝不重执行；**DONE 的缺失绝不解读为「未执行」**。
- **🔴 授权闸（你点中，必须显式遵守）**：新增 `_TS_REQUEST_LEDGER` 是**新的生产数据结构与写入**，当前**无创建/启用授权**（与 TS_WRITE_FREEZE / M2 clearance 未发 / 阶段一 PASS 暂缓 / HOLD-NO-GO 一致）。故 **账本推迟至显式授权（Rita clearance + 解冻）后方可创建/启用；当前不创建、不启用，本草案不构成启用**。即幂等键*契约*已设计，但其*实现/启用*受授权闸限制 —— 与全程零生产写红线一致。

### L2 · 序列化防碰撞 + 对账关联 → 接受，补编码细则
- **原 K2 不足（你点中）**：`typeTag|value` + `\u0001` join 仍可能碰撞（值含 `|`/`\u0001`、数组乱序、日期时区漂移、数值边界、null/空串混淆）。接受并补细则：
  - **长度编码 / 转义**：每格编码为 `TAG:LEN:PAYLOAD`（LEN = 字节长），杜绝分隔符碰撞；或每格 `JSON.stringify([type, value])` 自定界（JSON 对类型自描述）。二者择一，需测试。
  - **数组规范化**：定义固定 / 排序规则（如按数值或字符串键排序后序列化），避免顺序不同同值。
  - **日期时区**：一律序列化为 UTC ISO-8601（不带本地时区），消除时区漂移。
  - **数值边界**：用 `JSON.stringify(number)` 范式（处理 NaN / Infinity / -0）；`1` 与 `1.0` 同数同码，但与 `'1'`（字符串）因 TAG 不同而不同。
  - **null / 空串语义**：`null` → `null|`、 `''` → `s||`（空串带 TAG）、 `0` → `n|0`、 `false` → `b|false` —— 四者编码相异，显式定义。
  - 目标：**不同输入 → 同一编码（碰撞）必须不可发生**。
- **对账关联（回应「仅凭哈希相同未必证本次写入」）**：后续独立读即便 payloadHash 相同，也**不单凭哈希归属**；须关联 `requestId + businessKey + 时间戳 + 操作者 + 并发记录`（谁/何时）才能归因。故账本 / 不确定日志条目须带 `requestId + businessKey + ts + actor`，对账交叉引用（呼应 K3 请求证据，非仅哈希）。
