## 1. 错误根因（可复现，file:line）

**缺陷位置**：`tools/diag_cleanup_20261101.js:135`

```js
const byUuid = {};
alive.forEach(r => { const k = r.uuid || '(EMPTY)'; (byUuid[k] = byUuid[k] || []).push(r); });
const dupGroups = Object.keys(byUuid).filter(k => byUuid[k].length > 1);
```

`r.uuid || '(EMPTY)'` 使**全部 UUID 为空的行坍缩成一个键**。这批行约 5,221 行（占存活 47%），
于是被计为 1 个 dupGroup 并贡献 **5,220 行 extraRows** —— 那不是「同 UUID 重放」，纯粹是聚合假象。

**修正**：新脚本 `tools/ts_l1l2_stratify.js` 把空 UUID 行单独进 `EMPTY_POOL`，**绝不参与** UUID 冗余统计。

复现命令（只读，零写入）：

```
node tools/ts_l1l2_stratify.js
# 输出 _tmp/evidence/l1l2_stratify_<date>.json
```

## 3. 更正后的 L1/L2 判据（正面回应 Tom N8）

Tom 2026-10-31 N8 的核心反对：**「行先后不能证明业务保留语义；底稿缺失一律 UNKNOWN、保留原状」**。
我方接受该判据，并据此重做分层。新判据**不依赖底稿**，也**不依赖行序**：

### L1 = EXACT（1,340 行 / 3,645 h）—— 我方主张可机器化认定

- 组内副本 **col0..13 逐列全同**，样本连提交时间戳（col0）都相同：
  - `rows=[4143, 7549]` submit 均为 `2026-04-03`
  - `rows=[4146, 7552]` submit 均为 `2026-04-03`
  - `rows=[4148, 7554]` submit 均为 `2026-04-07`
- **关键**：因为副本逐列恒等，**「保留哪一行」不产生任何业务差异** ——
  我们**不需要**用行序去证明业务保留语义（那正是 N8 反对的东西），
  而是「内容恒等 ⇒ keeper 的选择与业务结果无关」。软标其余副本后，表内剩余内容**逐字节相同**。
- 服务端 CAS（`tsSoftDelGuarded`）对 keeperHash 的校验同样满足：任一副本哈希相同。

### L2 = TIMEONLY（227 行 / 401.5 h）—— 我方主张标 UNKNOWN、保留原状

- 仅录入时间不同（如 `2026-08-03` vs `2026-04-02`），**有实质差异**。
- 保留哪一条录入时间属业务判断，**非技术可裁定** → 按 N8 保留原状，请 Rita 裁定或逐组核实。

### 绝不动 = MIXED（0 行）与 EMPTY 池（5,221 行）

- MIXED 实测 0 组，无需处理。
- EMPTY 池 5,221 行无法用 UUID 建立同一性 → 按 N8 标 UNKNOWN、保留原状。
  （若日后要用内容指纹去重，属**另一套判据**，须另案提证，不在本次范围内。）

## 4. MIXED = 0 的证据意义（请 Tom 重点裁定）

在 1,567 组同 UUID 副本中，**业务字段（col1..13）存在差异的组数为 0**。

推论：若这些是「两条独立业务记录碰巧共用 UUID」，则姓名/日期/项目/工时/类型等字段
不可能 1,567 组全部一致。MIXED=0 与「同一条源记录被重复落库（重放）」完全吻合，
与「独立业务记录撞 UUID」不相容。

配合代码事实：
- `Code.js:305 submitBatch` —— 现场生成**全新** UUID；
- `RemoteActions.js:78 tsAppendRows` —— **原样落调用方传入**的 UUID。

故生产表中「同 UUID 出现多次」只能来自：调用方传入了已存在的 UUID（重放），
或批量写入的重复执行。**不可能**来自两次独立填报。

请裁定：EXACT 层是否可由「UUID + 逐列恒等」机器化认定，而不必逐组人工核实。

## 5. 我方此前另一处不实陈述的更正

我方早前称「可追到 2026-09-11~13 那 16 批次 appendRows 写入日志」以建立逐行溯源。
**经实拉 `_TS_WRITE_LOG` 验证，该说法不成立，予以撤回**：

- 日志结构为 3 列：`时间 | 动作 | 明细`，共 **1,371 条**（2026-09-11 11:29:53 → 2026-10-31 17:18:01）。
- **明细只含汇总计数**（例：`req=1519 wouldWrite=575 skipDup=944 skipLeave=0`），
  全文 32 位 hex（UUID 形态）出现 **0 次** → **无法逐行溯源**。
- 16 批次 appendRows 确为真实（全在 09-11~13：真实写入 9 条 + dry 7 条，
  真实写入合计约 5,334 行），但**与 UUID 冗余 1,567 行在数量与可归因性上均不匹配**，不能用作逐行证据。
- 取证脚本：`tools/ts_writelog_forensics.py`（只读）；原始转储 `_tmp/evidence/writelog_full_20261101_011014.json`。

**结论：L1 的成立不依赖写入日志，而依赖「UUID 同一性 + 逐列恒等」本身。**
