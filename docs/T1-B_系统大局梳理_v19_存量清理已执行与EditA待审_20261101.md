## 第三节 · A5 期锁旁路 —— 我方补披露（新增）

**事实**：线上 `RemoteActions.js:1011-1056` 的 `repairLegacyLeave` 直接
`sh.getRange(rn, 15, 1, 3).setValues([[true, OP, now]])` 写 **O/P/Q**，
**不经 `_plGuardPatch`**，因此**不受 period-lock 期锁拦截**；它有 `LockService` 防并发、幂等、`mode=undo` 可回滚、受 `REMOTE_TOKEN` 门控。

这是我方此前写者覆盖清单**未列全**的旁路（你方 W4/A5 待核项），**现主动披露**：
- 该旁路**是**今晚存量清理得以在 lock 期内完成的原因（无需 B2 放开期锁、也无需 B1 部署 softDelGuarded）；
- 但它是既有能力而非新开后门：V4.3.83 起即在线，设计用途正是「软删遗留噪音行」；
- 风险面：**任何持有 `REMOTE_TOKEN` 者**可用它在锁定期写 O/P/Q → 建议纳入你方 A5 与最小权限整改范围。

**我方处置**：已把 `repairLegacyLeave` 纳入 `tools/ts_post.py` 的 `WRITE_ACTIONS` 白名单，
即**仍受 `TS_WRITE_FREEZE` 冻结闸约束**——不因它绕过期锁而自动放行。

补丁全文见同仓 `docs/EditA_并发窗口根治_精确补丁_20261101.md`。要点：

实拉线上 `PeriodLockGuard.js:494` 确认 `lockPreWrite` 是**函数** `(rows,policy)=>{rows,duplicates}`；
`dedupInsideLock` **根本不存在**（全库 0 命中）。

**正确改法（纯 `RemoteActions.js` 单文件，零改 PeriodLockGuard）**：

| file:line | 问题 | 改法 |
|---|---|---|
| `RemoteActions.js:96-105` | 锁外读 `exist{}`（取锁前快照，不含并发在途行） | 删除；改调新函数 `_tsDedup(rows, _tsReadUuidSet(sh), force)` 仅作**提示性计数** |
| `RemoteActions.js:107-117` | 锁外据 `exist{}` 决策 `toWrite` | 删除（逻辑移入锁内，杜绝双份漂移） |
| `RemoteActions.js:127` | `_plGuardedInsert` 未传 `lockPreWrite` → `:494` 锁内重核被跳过 | 传 `lockPreWrite: function(rowsIn, policy){ return _tsDedup(rowsIn, _tsReadUuidSet(sh), force); }` |
| 新增 `_tsReadUuidSet(sh)` / `_tsDedup(rows, exist, force)` | — | 纯函数、依赖注入 `exist`，锁外提示与锁内权威复用同一逻辑 |

**验收**：① `node --check` + 推码后 FFFD=0 ② 单发含重复 UUID → `duplicates>0`、无新增重复 ③ **并发负例 N1**：同批 UUID 并发 2–4 请求 → 该 UUID 最终仅 1 行（改动前会 2+ 行）④ 期锁行为不变。
