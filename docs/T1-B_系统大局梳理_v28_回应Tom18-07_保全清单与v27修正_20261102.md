### 3.5 v27 技术修正（你方命中的错误，逐条更正）

#### 3.5a 线性化时点（你方正确）：v27 §4.2 定义有误，已更正

- v27 原文（错）：「冻结生效的线性化时点 = `tsSetFreeze` **取得锁的时刻**」。
- 更正：**线性化时点 = 冻结配置（TS_SERVER_FREEZE）在同一把 `getScriptLock()` 内 `setProperty`+`flush` 成功提交之时刻**。
- 代码 `RemoteActions.js`（C-v4-1）本身已是「取锁→setProperty→flush→释放」，提交点在锁内，意图正确；仅文字定义误述，已改为「成功提交时刻」。

#### 3.5b tryLock(30000) 验收语义（你方正确）：v27 §4.2 V1 有误，已更正

- v27 V1（错）：「写者持锁 5s 期间调 `tsSetFreeze=1` → 返回 `LOCK_BUSY_FREEZE_NOT_APPLIED`」。
- 更正：`tryLock(30000)` 在写者持锁 5s 时会**等待该写者释放（≤30s 内）后再取得锁并提交冻结**，故返回 `ok:true`（**非** LOCK_BUSY）。这正是你方要求的「全部写者和切换者共享有效锁且**写完成才可得出结论**」。
- 修正后 V1：`tsSetFreeze=1` 在写者持锁 5s 期间调用 → 阻塞至写者释放 → 提交冻结 `ok:true`、`TS_SERVER_FREEZE=1`；此后任何写者 `waitLock` 后重读冻结位 → 读到 1 → 拒绝且零落盘。
- 备选（若你方要「失败即拒」语义）：将 `tryLock(30000)` 改为 `tryLock(0)`，拿不到锁立即返回 `LOCK_BUSY_FREEZE_NOT_APPLIED`（不等待、不提交）。代价：冻结可能需多次重试才能在某安静窗口落定。两种语义我方均可实现，请你方裁定采用哪种。

#### 3.5c 跨项目锁域（你方正确）：v27 §4.2 C-v4-3 不足，已修订

你方：「跨项目用表格读写重读不构成原子 CAS，租约过期的旧持有者仍可能写入，需真正原子协调及 fencing，或收敛为单写者。」

承认 v27 C-v4-3 的「表读写 + revision CAS」**非原子 CAS**（读-写间有竞态），且**无 fencing**（租约过期旧持有者仍可写）。修订为二选一：

- **CF-A（fencing 令牌）**：协调表增 `E=epoch(int)`；每个写者写前读取当前 epoch 并随写入携带自身 lease epoch；守卫在写入前校验 `leaseEpoch == currentEpoch`，否则拒绝（陈旧写入被 fencing 挡下）。需配套：lease 过期即 epoch++。

我方建议 **CF-B（不拆分写路径）+ 仅在确需拆分时启用 CF-A**。请你方裁定。
