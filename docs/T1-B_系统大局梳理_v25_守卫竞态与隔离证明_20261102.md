## 第二节 Edit C v3：你方 17:09 新提的三条缺陷，逐条落法

### C-R1 在途写与守卫切换竞态（新增，v22 版 Edit C 未覆盖）

**问题**：v22 版守卫只在入口/触发器进入前读一次 `TS_SERVER_FREEZE`。若读取时值为 0（放行），随后配置被翻为 1，而该次业务写仍在途（尚未落盘），则该写在冻结生效后仍会落盘 —— 守卫对「已进入的在途写」无效。

**改法（双点校验，不嵌套取锁）**：

1. `RemoteActions.js` 新增（紧邻 `_tsWriteLog` 之前）：
```javascript
function _tsFreezeState() {
  var v;
  try { v = PropertiesService.getScriptProperties().getProperty('TS_SERVER_FREEZE'); }
  catch (e) { return { failClosed: true, reason: 'read_error' }; }
  if (v === null || v === undefined || String(v).trim() === '') return { failClosed: true, reason: 'missing' };
  var s = String(v).trim();
  if (s !== '0' && s !== '1') return { failClosed: true, reason: 'bad_value' };
  return { failClosed: false, frozen: s === '1' };
}
function _tsFreezeRecheck() {
  var st = _tsFreezeState();
  if (st.failClosed) throw new Error('SERVER_FREEZE(' + st.reason + ')');
  if (st.frozen) throw new Error('SERVER_FREEZE(switched_during_write)');
  return true;
}
```
2. `PeriodLockGuard.js:490`（取锁后）与 `:509`（`bizWrite` 之前）之间插入 `if (typeof _tsFreezeRecheck === 'function') _tsFreezeRecheck();`
   —— 关键点：**二次校验发生在持锁之后、落盘之前**，与守卫切换构成同一临界区，消除「读到 0 → 配置翻 1 → 在途落盘」窗口。
3. 入口层守卫保留一次性判定（快速拒绝），锁内二次校验处理竞态；两者不是重复，是两道不同窗口。

**验收**：
- V1：置 `TS_SERVER_FREEZE=1`，在 `bizWrite` 内注入 5s 延迟，于延迟期间翻转配置 → 预期抛 `SERVER_FREEZE(switched_during_write)` 且该次写入零落盘。
- V2：配置为 0 且全程不变 → 正常写入不受影响（回归）。
- V3：配置读取抛异常 / 缺失 / 值为 `2` → 均 fail-closed 拒绝。
- 边界（不做过度声称）：本编辑只解决**单项目内**的「入口判定与落盘之间」的窗口，不解决跨项目互斥，也不声称覆盖「已在锁内且已过二次校验后、配置才翻转」的极小残窗 —— 该残窗我方如实列出，交你方裁定是否需进一步收紧（可选项：落盘前第三次校验）。

### C-R2 拒绝日志本身是写入（新增，你方指出正确）

**问题**：`_tsWriteLog`（`RemoteActions.js:65-77`）会 `getSheetByName('_TS_WRITE_LOG')`，**不存在时 `insertSheet`**（:69-72）—— 即日志动作自身是写动作，且可能建页。若冻结期仍写日志，则「冻结」名存实亡，并引入递归（日志写又触发守卫）。

**改法**：拒绝路径**不写生产表**，改写入 ScriptProperties 环形缓冲：

```javascript
var TS_DENY_LOG_CAP = 200;
function _tsDenyLog(action, reason, extra) {
  try {
    var sp = PropertiesService.getScriptProperties();
    var arr = [];
    try { arr = JSON.parse(sp.getProperty('TS_FREEZE_DENY_LOG') || '[]'); } catch (e) { arr = []; }
    if (!Array.isArray(arr)) arr = [];
    arr.push({ t: new Date().toISOString(), action: String(action), reason: String(reason), extra: extra || null });
    while (arr.length > TS_DENY_LOG_CAP) arr.shift();
    sp.setProperty('TS_FREEZE_DENY_LOG', JSON.stringify(arr));
  } catch (e) { /* 日志失败不得阻断拒绝本身：拒绝已生效为第一优先级 */ }
}
```
- 拒绝路径统一改调 `_tsDenyLog(...)`，**不再**走 `_tsWriteLog`；`_tsWriteLog` 仅保留于放行路径。
- 缓冲定长 200，**不可能无限增长**（回应「须限定安全行为」）。
- 日志通道在守卫判定之前短路，**不递归**。
- 读取方式：`?action=denylog`（登记为只读动作，见第三节）。

**验收**：置 1 后连续发起 300 次被拒请求 → `_TS_WRITE_LOG` 零新增行、生产表无任何变化、`TS_FREEZE_DENY_LOG` 长度恰好 200。
