## 修订 1（对应 00:29 唯一剩余缺口：跨请求互斥机制）

**v3 错误的承认**（已核实属实）：「同一函数栈内顺序执行 / GAS 单实例执行顺序」只说明单次调用内部先重核后写，**不构成不同请求/执行实例之间的互斥**；GAS 同一 script 可并发多个执行实例。v3 该表述撤回。

**v4 修订（采用 GAS 原生 LockService，script 范围跨执行互斥）**：

- **M8 改为「LockService 临界区」**：
  - **锁域**：参与入口 = **同一 script 项目内**的写入口（以已只读取得的 HEAD 快照中的写入口为准，编码前复核）；所有参与入口共用同一具名 script 锁（`LockService.getScriptLock()`，如锁名 `PERIOD_LOCK_GUARD`）。
  - **流程**：`tryLock(超时)` → **失败即零写（拒该请求，不做无锁写入）**；成功后在**锁内**重读稳定行标识 + 当前版本/期间 → 与请求提交版本不符即拒 → 业务写完成 → `finally` 释放锁（含异常路径释放，`hasLock` 确认）。
  - **取得锁对象 ≠ 取得锁**：仅 `tryLock` 返回 true 视为取得互斥（遵官方语义）；不得以持有锁对象宣称互斥。
- **范围缩小（诚实登记）**：LockService 的 script 锁域**仅覆盖同一 script 项目内的参与入口**；**跨项目入口不能仅凭同名 guard 声称共享 script 锁域**——跨项目写者继续列为**未覆盖**（仅 X2 检测告警）。
- **不引入**：分布式锁、自动恢复、事务机制。

**R10b 重写（两个独立请求的交错时序，非"串行阻止"一句话）**：

| 时序 | 请求 A（参与入口） | 请求 B（参与入口） |
|---|---|---|
| t1 | `tryLock` 成功（取得 PERIOD_LOCK_GUARD） | `tryLock` 失败（超时） |
| t2 | 锁内重读目标行：期间=10 月、版本 V1，与提交版本相符 | —— |
| t3 | 业务写完成（改 9 月行的请求在此步根本进不来——它连 t1 都过不了） | 返回拒（零写） |
| t4 | 释放锁；请求 C 随后 `tryLock` 成功 → 锁内重读相符 → **放行** | —— |

- **合法后续请求放行**：A 释放锁后，后续合法请求可重新取锁、锁内重读相符即写入——**不将一切后续合法请求无条件拒绝**；后写者被拒的判据是「取锁失败」或「锁内实读与提交版本不符」，而非"前面有人写过"。
- **R10c 不变**：外部（跨项目）写者任意时刻改同行 → 未覆盖，仅 X2 告警 + 人工处置。

**R12b 处置补充（吸收 00:29 X2 段）**：业务写中途异常 → 记录「不确定批次」（哪些行已写/未写不确定）交人工核查；不自动重试、回滚或补偿；X2 检测覆盖能力在实现验收前不作为"所有部分写均可识别"的保证依据。
