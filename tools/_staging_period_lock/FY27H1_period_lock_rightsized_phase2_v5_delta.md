## 修订 1（写完成边界：释放锁前必须提交）

**问题承认**（属实）：v4"业务写完成→释放锁"未明确"写完成"的提交边界——SpreadsheetApp 写路径下，未 flush 的待处理变更在释放锁后仍可能由后续持锁者触发提交，"写完"不等于"已提交"。

**v5 修订**：

- M8 流程补全为：`tryLock` 成功 → 锁内重读稳定行标识 + 期间 + 版本 → **独立期间门禁＋版本检查**（见修订 2）→ 全部通过才业务写 → **释放锁前 `SpreadsheetApp.flush()` 提交待处理变更** → 释放锁。
- **完成边界声明**：若实际使用其他写 API，须明确其各自的完成边界，不一概套用 flush；本设计以 `SpreadsheetApp.flush()` 为提交边界。
- **异常语义**：写/提交异常 → 沿 R12b 登记「不确定批次」→ finally 释放锁；**不以 finally 执行或 hasLock 结果判定写成功**；不做无条件刷新重放、不做自动补偿。

## 修订 2（R10b：取锁与期间门禁分离）

**错误承认**（属实）：v4 R10b t3 括号"改 9 月行的请求连 t1 都过不了"把锁竞争与业务期间门禁混为一谈——取锁成功只证明取得互斥，**不承载任何期间合规含义**；9 月请求在无竞争时同样能取锁成功，必须在锁内被独立期间门禁拒绝。

**v5 修订**：

- 临界区内顺序写死为四步：**① 取锁成功（tryLock true）→ ② 锁内重读稳定 ID/期间/版本 → ③ 独立期间门禁（fillDate < 2026-10-01 → 拒）＋版本检查（与提交版本不符 → 拒）→ ④ 全部通过才业务写 → flush → 释放锁**。
- **明确声明：锁本身不识别月份**；期间合规由锁内门禁逻辑判定，与互斥机制职责分离。仅版本相符不能代替期间合规。
- **新增反例 R10d**：**无竞争场景下 9 月请求 tryLock 成功 → 锁内重读期间为 9 月 → 期间门禁拒之（零写）**。证明拒因是门禁而非锁竞争。
- **R10b 拆为两个分支**（取代原单一时序）：
  - **B1 锁竞争分支**：A 持锁期间 B tryLock 超时 → B 零写被拒（A 持锁覆盖 B 等待窗口为一个测试安排）；
  - **B2 等待后重核分支**：B 等到锁后重新读行期间/版本 → 相符放行 / 不符拒（**非并发即必超时**）。
  - 合法后续请求 C：A 释放锁后取锁成功 → 锁内重读相符 → 放行（不一律拒绝）。

## 修订 3（术语更正：script 锁无命名参数）

**更正**（属实）：`LockService.getScriptLock()` 无自定义锁名参数；v4 中"锁名 PERIOD_LOCK_GUARD"表述撤回收敛为：**同一 script 项目内所有参与入口共用同一个 script 锁（getScriptLock 单例）**；`PERIOD_LOCK_GUARD` 仅作代码内的本地约定标识/注释用途，**不是可命名的独立锁域**——不产生"同项目可按名称划分多个锁域"的错觉。
