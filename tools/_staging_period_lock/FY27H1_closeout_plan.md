# T1-B · 生产工时表 FY27H1 关账（period-lock）方案 · 完整计划

> 状态：**PLANNING（规划中）** — 尚未编码，全程零生产写操作。
> 日期：2026-10-24
> 范围：生产工时表 `DB_工时流水` + ts-manager 填报页 `1FPAwV50`（脆弱实时系统）
> 关联：与在途「请假提示 A 包装」**解耦**，独立改动、独立评审、独立上线。

## 1. 目标与背景

- 把 `fillDate < 2026-10-01` 的工时记录**机械关账**，清理后只允许继续填报十月起的日期。
- 等价于「收尾 FY27H1」：FY27H1 = 2026-04-01 ~ 2026-09-30（含更早历史一并冻结）。
- 价值：消除「有人回头改九月 / 补录旧日期」把 H1 报表、考评（FY27H1 口径已定）、对账全部搞乱的风险——对脆弱实时工时系统是标准 *period close* 控制。

## 2. 范围与锁定口径

- **锁定键**：`fillDate`（工时发生日），非提交日、非行写入时间。
- **阈值**：`fillDate < 2026-10-01` → 关账；`2026-10-01` 起（含十月、十一月、未来）全开。
- **作用对象**：生产工时表 `DB_工时流水` 经 ts-manager 填报页写入的行。
- **不波及**：请假提示读历史镜像（只读，不受影响）；已在途的请假提示部署。

## 3. 设计决策（已与 Rita 定稿）

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 锁类型 | **软锁** | 默认只读+灰标；Rita/sysadmin 可**一键解锁**做更正并留审计。硬锁会逼出线下影子表，反而更乱。 |
| D2 | 拦截位置 | **提交函数拦截**（主）+ sheet 保护（次，防御） | GAS 写入能绕过 sheet 保护，故必须在提交函数里拦；sheet 保护仅作二次警示。 |
| D3 | 关账顺序 | **verify-then-lock** | 先扫 H1 行做完整性/总额核验，只标缺陷供审、**不动数据**；确认后再锁。 |
| D4 | 与请假提示关系 | **解耦** | 独立改动，单独走 staged + 一键关闭开关 + fail-closed，不跟 v5 混推脆弱实时系统。 |
| D5 | 「清理」口径 | **对账核验后锁**（Rita 选定） | 扫 H1 行标疑似缺陷→Rita 审→（可选）修正→锁。不盲目动历史数据。 |

## 4. 操作流（Phase 0 → 3）

- **Phase 0 · 只读 · H1 对账核验扫描器**（可立即做，零写）
  - 读 `DB_工时流水` 的 H1 行（fillDate ∈ 2026-04-01~09-30）。
  - 规则：① 应填报人/项目**缺月**检测；② 月工时**合理性**（>自然日×24、为负、应为非零却为 0）；③ 日期**合法性/跨月错位**；④ 项目/人员编号**引用完整性**（对 BD list / 主库）；⑤ 已知缺陷模式（`#REF!`、空白关键列、重复行）。
  - 产出：**疑似缺陷清单**（只报告，改 0 个单元格）。
- **Phase 1 · 只读 · 拉 ts-manager 真实 HEAD 定位插入点**（当前阻塞）
  - `gas_pull` `1FPAwV50` 返 HTTP 400（身份未验证/凭据范围，CLASP_MAP 列「尚未验证身份」）。
  - 解除：Rita 浏览器重授权一次 GAS 访问 **或** Rita 贴提交函数片段。_blocker_。
- **Phase 2 · 设计 · 改造草案**（HEAD 核验后）
  - 提交函数加 `fillDate < 2026-10-01` guard（拦截+友好提示）。
  - **一键关闭开关** `FEATURE_ENABLED`（默认 true 锁 / false 全开，应急可关）。
  - **解锁审计**：新增 `工时表解锁审计` tab，记录 谁/哪行/何时/原因；解锁仅限 Rita/sysadmin 角色。
  - **灰度 + fail-closed 回滚** 脚本（参照请假提示 STAGE3 runbook 纪律）。
  - 带行号草案交 Tom 技术评审。
- **Phase 3 · 生产写 · 需 Rita 显式 GO + 双授权闸门**（gate A=Tom 技术 clearance / gate B=Rita 授权）
  - 改提交函数 → 版本化 deploy（URL 不变、保留 ANYONE_ANONYMOUS、验行数）→ 灰度（仅 Rita 本人→全量需二次确认）→ fail-closed 回滚。

| # | Tom 边界意见 | 收敛为设计约束 |
|---|---|---|
| 1 | H1 扫描 4/1~9/30 与锁定所有 10/1 之前（含更早历史）**不等范围**；不能以 H1 核验覆盖全部锁定对象 | 扫描分两段独立报告：① H1（4/1~9/30）② pre-H1 更早历史；边界时区用**明确业务日解析**，**禁止失败解析变成放行**；空/非法/多格式日期单列；缺月/应非零/合理性上限须**来源规则支持**，仅疑似清单，**不作人员考评或薪酬裁定** |
| 2 | 仅 guard 新 fillDate 不能防「把旧行日期改到 10 月后」 | 写网关**双向检查**：新增看新日期；修改/删除同时检查**原记录期间 + 新记录期间**（覆盖改日期/批量导入/管理员/触发器/API 等所有真实写入口）；缺旧值/身份/锁状态即拒该写入；「未来日期全开」作为**独立业务 policy 标志**，不默认随本改动开启 |

| 4 | 锁检查与写入须同一原子/并发边界 | 以**稳定行标识 + 预期版本**绑定（不以可漂移物理行号作唯一身份）；审计与写入一致性、失败补偿、只追加防篡改、权限与保留期先设计；**审计 tab 本身也是新生产写，须另行授权** |
| 5 | 保留 `ANYONE_ANONYMOUS` 部署不能当默认安全前提 | 先从**已授权取得的固定源码/部署资料**确认真实项目、执行身份、入口与信任边界；**不为 HTTP400 主动重授权/扩权限/调用生产**；匿名访问与可靠主体/管理员豁免隔离作为 Phase 2 显式设计点 |
